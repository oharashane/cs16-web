0. The short version

What exists. Real Counter-Strike 1.6 servers (ReHLDS, in Docker) that a browser can join. The browser runs the actual GoldSrc-compatible engine — Xash3D FWGS compiled to WebAssembly, with a reverse-engineered CS 1.6 client — and speaks to a small Go relay over WebRTC data channels; the relay turns those into the UDP the game server expects. One server, six switchable game types, a lobby that asks for a name and a password, and a darkoak room with twenty-six tools that can start, stop, retune and interrogate all of it. A friend with real Steam CS 1.6 can join the same server through a playit tunnel today.

What it was. A five-week sprint in August–September 2025, with the coding tools of that year, that reached "it works" twice and left behind a hand-patched minified engine, three containers with 1.7 GB of maps baked into each, thirty-two planning documents, and a CSDM plugin that crashed the server on every team join for a year without anyone seeing it as a crash. It was a genuine proof of concept and it proved the concept.

What happened to upstream. The engine port it was built on — yohimik's webxash3d-fwgs — was the best thing in this space in 2025 and was deleted by its author in August 2026, with every npm package marked "will be removed". Everything needed to rebuild it survives, in a fork, in the npm tarballs saved to ~/darkoak-backups/, and in the upstream FWGS engine itself, whose maintainers were never keen on a web port and said so. The wider GoldSrc ecosystem is healthy: ReHLDS and ReGameDLL shipped in May 2026, AMX Mod X 1.9 shipped in April 2026, the CS 1.6 client project is committed to daily.

Who else. play-cs.com has done this commercially since 2019, on an older engine, and is the proof that a few thousand people want it. Seven GitHub projects have shipped something in the last eighteen months, and three of them are genuinely multiplayer — every one of those three by using yohimik's server image or reimplementing his relay (§5). Nobody has built the museum part: the catalogue, the previews, the provenance. The tools to build it — browser BSP and MDL renderers — exist and are actively maintained.

The one performance finding. The lag is not the network. Browser-to-relay is under a millisecond; the game's own ping on the same machine is ~47 ms, and dropping the update rate from 100 to 20 halves it. Section 7 has the table and what to do with it.

The plan. Section 12: a foundation of servers-as-records created on demand, a catalogue where a map is an artifact with a preview and a history, a client that can load one map at a time instead of 275 MB, and a room that lets one person run the whole thing from a chat. Invite-only by construction, not by afterthought.

1. History, 2025: six plans in five weeks

The repository's first commit is 9 August 2025, "initial from ghatgpt5". The last 2025 commit is 7 September, "tried and failed to get BHOP and CSDM FFA working". Seventy-six commits in between, and thirty-two documents whose filenames tell the story better than any summary could: PLAN A, PLAN B, PLAN C 1 through PLAN C 9.5 SOME SIGNS OF LIFE, PLAN C X OMFG IT WORKS, PLAN C XX RETROSPECTIVE, PLAN D 1 MAKE IT AWESOMER, PLAN E 1 MULTISERVER, PLAN F 1 PERF AGAIN, STUN FOR STUPID IMAC, TURN FOR STUPID IMAC, TURN TAKE TWO.

Read in order they are a record of what building with LLMs was like in mid-2025 — GPT-5 for planning, Cursor and "claude4sonnet" for code, Claude Code arriving on day three ("claude code to the rescue… but ran out of claude pro daily credits right before we actually crossed the finish line") — and of a person keeping the thread when the tools lost it. The commit "ok it works again, for real" comes after "fixed some things but client still not connecting at ALL to server anymore over rtc", which comes after "omfg it works".

Plan A (9–10 August): modify the engine

The first idea was the principled one: add a transport abstraction to Xash3D FWGS in C — net_transport.h, a WebRTC implementation for Emscripten builds, an Emscripten JS library bridging data channels — and rebuild the engine. The document for it is written in the past tense of a finished thing ("Implementation Status: COMPLETE… Zero-Compromise Browser Gaming") and it never ran: the engine crashed with RuntimeError: unreachable during Touch_Init(), and, as PLAN A STATUS found, it crashed the same way without the modifications. The build environment was the problem, not the transport. That finding is the most important thing Plan A produced: it stopped a week of debugging the wrong layer.

Plan B (10 August): the same, more carefully

A half-day plan to stabilise the build with assertions and a bigger heap, then add the transport in "two places only". It was written and not executed; Plan C started the same day.

Plan C (10–16 August): use yohimik's client, build the relay

The turn that worked. Instead of rebuilding the engine, take the WebAssembly build yohimik had already published — as a Docker image, yohimik/cs-web-server, because "we could never get the source code from the GitHub repo to work" — extract its client files, and write a relay that speaks whatever that client speaks. Plan C has eleven documents because that turned out to be harder than it sounds, for three reasons that are each worth knowing:

The client expects the server to send the WebRTC offer.
Standard WebRTC has the caller offer. yohimik's client opens a WebSocket and waits. Every relay written to the standard flow sat there forever ("WS open → no client hello → idle → 1001 close"). Found by reading webrtc.ts:115-137 in the upstream source after ChatGPT suggested capturing the handshake with a proxy. PLAN C 4 XASHRTC RESEARCH is that capture: the exact {event, data} envelope, the offer-first flow, the observation that "multiple offer/answer rounds" happen. The 2026 relay still speaks exactly this.
The engine's networking is not reachable from JavaScript from outside.
Two days of "js interception not possible" — patching sendto, WebSocket, addFunction — before accepting that the compiled bundle had to be modified. Which is why the 2025 client is a minified file with three sed patches documented in MANUAL_MODIFICATIONS.md. (In 2026 this dissolved: upstream had by then exposed the network layer as a TypeScript interface, so the 2026 client is a hundred and fifty lines of source and no patches.)
The engine crashed on connect with "Cannot perform Construct on a detached ArrayBuffer".
WebAssembly memory grew during the handshake, the JS view of it was invalidated, and the send path used the stale view. The fix that finally worked (PLAN C XX RETROSPECTIVE) was a sed on the minified bundle changing INITIAL_MEMORY||134217728 to 536870912 — 512 MB up front so memory never grew. Runtime Module configuration was ignored by the compiled bundle, which is why every attempt to set it from the page did nothing. The retrospective's own lesson: "Always verify ACTUAL container state, not just git commits" — a Docker volume mount had been serving stale files for a day. (Upstream fixed the underlying bug in engine 1.2.1, October 2025; the 2026 client has no memory patch.)

Along the way, Plan C also found that Reunion — the Metamod plugin that lets non-Steam clients onto a ReHLDS server — needs a SteamIdHashSalt to load at all, and that with several browsers on one LAN the server rejected all but the first ("Your SteamID is already in use"). The fix, cid_RevEmu2013 = 10, gives every browser player the same identity, VALVE_ID_LAN. The document that records it says "DANGER: only good for LAN, don't go public with it", and it is still in place; §6 returns to it.

The architecture at "OMFG IT WORKS" (14 August) had four hops: browser → Go WebRTC server (yohimik's own, lifted from his repo) → Python aiortc relay → ReHLDS. The Python layer was the original relay from Plan A; the Go layer was added because it already spoke the client's handshake. Two WebRTC implementations back to back, joined by HTTP and a WebSocket. It worked, and it was the first thing Plan E removed.

Plan D (15–17 August): LAN, and the iMacs

Making it work on other machines in the house, which is where two long-running threads begin. Host networking for Docker, so ICE candidates carried the machine's real address rather than 172.17.x.x (NETWORK MODE ANALYSIS is a careful, correct essay on why). And one iMac that would not connect: it generated host candidates and never sent connectivity checks. Three documents try STUN, then TURN, then TURN again, and the commit "roll back stun/turn stuff, didnt help anyway with particular imac issue (ubuntu worked fine tho)" closes the thread without an answer. It is still open; nothing in the 2026 work touched it, and the new candidate handling (§3) changes the shape of what that iMac is offered, so it is worth re-testing before assuming.

Plan E (18 August): one Go relay, three servers

The Python relay goes; the Go server gains the UDP bridge and a discovery loop that scans ports 27000–27030 every three seconds and opens a WebRTC listener on an "offset port" (27015 → 8015) for each server it finds. The offset scheme existed only because the patched client could not take a server address, so the port was the address. Three Docker containers — classic, deathmatch, gungame — each built from a Dockerfile that COPY'd all 1.7 GB of shared content into the image. Plan E's document also proposed the deployment that was never built: a VPS with a public IP for WebRTC, WireGuard back to the house, and "Cloudflare Pages (Future) — Static Assets, Museum/Browse". The word museum is in the 18 August plan.

The CSDM week (18–20 August)

"CSDM, weapon menus back through hacks", "CSDM 2.x working with guns menu!", "classic, deathmatch, gungame servers working perfectly". Getting CSDM 2.1.3 — a 2013 plugin — to run on a 2023 ReHLDS with a 2013 AMX Mod X took the better part of three days and a csdm.cfg that would be deleted three weeks later.

Plan F (20–21 August): TURBO

The Retina problem. On an Intel iMac the engine "sputters"; on an RTX 3090 it does not. PERFORMANCE-TEST-RESULTS is a proper experiment log: five approaches that had no effect (because the compiled bundle ignored Module), one that had an effect and broke the display (resizing the canvas backing store — "zoomed into bottom-left corner" — which proved rendering was the bottleneck), and the one that worked: overriding window.devicePixelRatio to 1 before the engine started, so a 2× display was drawn at 1×. "DPR config works! scaling does not." The turbo page, the turbo zip and the scaling were reverted; the DPR clamp stayed and is the "Fast" option in the 2026 lobby.

The last two commits (1 and 7 September)

"added some maps, trimmed the valvezip from hl maps, disabled FF" and "tried and failed to get BHOP and CSDM FFA working". The second one deleted csdm.cfg (309 lines) and enabled csdm_ffa.amxx. From that day until 6 September 2026, joining a team on the deathmatch server crashed it. hlds_run restarts within ten seconds, so it never looked like a crash — it looked like a weapons menu that gave you nothing. BUNNY_HOP_FFA_TROUBLESHOOTING, the largest document in the folder at 3,700 words, is the record of trying to fix the symptom.

What 2025 got right

The shape. Real ReHLDS with real plugins, not a wasm dedicated server; a thin relay that copies bytes and interprets nothing; discovery rather than configuration; the game's own client in the browser rather than a reimplementation. Every one of those held up. And the documents, for all their emoji, recorded what was tried and what happened, which is the only reason the 2026 work took a day: the ArrayBuffer retrospective, the handshake capture, the DPR experiment, the LAN-identity note and the "DANGER" beside it were each read and each saved hours.

3. How it works today

The client

web/ is a Vite project of four source files. webrtc.ts subclasses the engine's Xash3D and supplies a Net: every datagram the engine wants to send arrives at sendto() and goes down the read data channel; every message on the write channel is enqueued into the engine's incoming buffer stamped as coming from the fictional server address. join(port) opens a WebSocket to /ws/<port>, answers the offer the relay sends, trickles candidates, and resolves when both channels are open; leave() tears that down and leaves the engine booted. main.ts is the lobby, the loader, the watchdog. The engine and the CS client come from two npm tarballs in web/vendor/ — the last versions ever published (§4).

The page fetches /valve.zip (274 MB, 4,126 files), unzips it in the main thread with JSZip into Emscripten's in-memory filesystem, writes extras.pk3 beside it, and starts the engine with -game cstrike. That unpack is the slow half of loading and has its own progress bar; it is also where the client's memory goes: ~464 MB unpacked plus the engine's heap. On a second visit the download is a 304 and the unpack happens again.

The relay

Five Go files, 1,300 lines with tests. Discovery scans 27000–27030 every three seconds with the game's own query packet and keeps a registry. A session is one WebSocket, one PeerConnection, one UDP socket and one registry row, created in one place and removed in one place. The data channels are unordered with no retransmits — the closest a data channel gets to UDP, and what the game protocol assumes. ICE uses one muxed UDP port for every session, so the outside world needs one forwarded port; the relay offers its real addresses plus one it cannot see, the tunnel's, at a lower priority. /api/sessions reports per browser: server, since when, datagrams and bytes each way, ICE round-trip. The static handler serves the built client, the 2025 client, and the zip, with cache headers that make a second visit cheap.

How a browser actually reaches the house

There are two doors and they are not the same door. HTTP — the pages, the client's files, the 274 MB zip, and the signalling WebSocket — goes through Cloudflare: cs16.darkoak.xyz is a tunnel to 127.0.0.1:27100, so it is HTTPS, it needs nothing open on the router, and it is where the admin key is asked for. The game's packets cannot go that way, because a Cloudflare tunnel carries TCP and WebRTC is UDP. They go over ICE to port 46089, and that port is reachable by whichever of these the visitor's browser can get to first:

ICE tries them in parallel and keeps the highest-priority pair that works, so the ordering is a preference, not a sequence of attempts: a browser in the kitchen takes the LAN path and never touches the tunnel; a laptop on the tailnet takes the tailnet path; a friend's browser fails the first two in a second and settles on playit. The tunnel candidate is injected by hand in signal.go at a priority just below pion's host candidates, precisely so that it never beats a direct path (§2, commit 2b0b148).

That list is shorter than it was. Until 7 September pion offered every address on the machine, which meant two more kinds. Docker's bridges (172.17.0.1, 172.18.0.1) are reachable from nowhere, and every browser spent a second failing on them before moving on. The machine's global IPv6 address was worse than useless: a browser can take it, and one did in the first public test below, which means the path in from outside depended on the router's inbound policy rather than the tunnel, and the house's own address was handed to every visitor as a matter of course. The mux is now built with UDPMuxFromPortWithNetworks(NetworkTypeUDP4) and an interface filter, so only the LAN and the tailnet are bound — checked with ss after the restart — and everyone else arrives by the tunnel, on purpose. Re-enabling IPv6 is one line, if it ever earns its place.

Verified 7 September 2026, joining https://cs16.darkoak.xyz/play in a headless browser and reading the nominated candidate pair from the browser's own statistics: page, client, zip, signalling and game all worked. It is the check that found the IPv6 path, and it is the check to repeat from a phone with wifi off, which is the only way to prove the tunnel carries a stranger.

The other tunnel, and the same bug in it

A native Steam client uses neither door: connect roosevelt-refuses.tun.ply.gg:9767 is a second playit tunnel to the game server, and it answers the game's own query packet from the public internet. But a tunnel is one address, and one address is precisely what ReHLDS mistakes for one player (§6) — so two people playing from real Counter-Strike clients could take each other's slots exactly as the three browsers did on the 6th. A tunnel cannot be talked out of this; it has no idea it is carrying two games.

So the tunnel is now pointed at the relay rather than at the game server. steam.go listens on 27515/udp, and for every distinct address beyond the tunnel it opens a socket of its own bound to its own loopback address, forwards to 27015, and remembers who asked so the answers go back to the right player. Addresses come from the same counter the browser sessions draw on, so the two can never collide; a client that has been silent for three minutes gives its address up. It is the browser fix again, in the one place the browser fix could not reach — about a hundred lines, with a test that puts two clients through it and insists the server sees two addresses. Proved against the live server: two queries from 127.0.0.1, arriving as 127.0.0.2 and 127.0.0.3, both answered.

One manual step remains, in playit's console rather than in this repository: the tunnel "cs 1.6 udp (hlds)" must forward to local port 27515 instead of 27015. Its public address, roosevelt-refuses.tun.ply.gg:9767, does not change, and neither does anything a player types. Until it is changed the ingress sits idle and tunnelled Steam players still share one address. Clients on the LAN are unaffected either way: they reach 27015 directly and already have addresses of their own.

The servers

timoxo/cs1.6:1.9.0817 is the base image — HLDS build 3378 with ReHLDS 3.13.0.788 (July 2023), ReGameDLL, Metamod-r 1.3.0.149, Reunion 0.2.0.13, AMX Mod X 1.8.2. Our Dockerfile adds only gettext and the shared addons; everything else is mounted. entrypoint.sh links maps, wads, sounds, models, sprites and overviews from shared/, copies the mode's addons over the image's, links plugins.ini and modes/, renders server.cfg with the two secrets, and runs hlds_run. A mode is modes/<name>.cfg (the cvars), modes/<name>.maps (the rotation) and a line in modes.json; modes/current.cfg is one exec line that amxx.cfg re-runs on every map, because a map load resets cvars the game DLL owns and server.cfg is not re-run on a map change.

The room

darkoak's cs16 room has three sources, as its minecraft room does: Docker for whether a server is up (and the only way this room changes that), the relay's API and the servers' consoles for the present, and the servers' own log files — every join, kill, chat line, map change and round result — read into rows every minute for the past. set_mode, change_map, set_cvar, start_server, stop_server, say_to_server, kick_player, run_rcon_command as the journalled escape hatch, and measure_lag, which reads the browser-to-relay hop and the whole path at once so they can be compared.

Tests

Three suites. The relay's Go tests include a full round trip with pion playing the browser. darkoak's suite (578) covers the room, the RCON client against a fake HLDS, Docker against a scripted daemon, and the log parser on real lines. And seven Playwright tests that drive the built client through the running relay to the live servers: lobby, in the game (asserted by the server's own console saying so), leave and rejoin without a second download, the name remembered, a refused password explained, that a player who vanishes does not hand their slot and their name to the next joiner, and — the one that reads the container's log — that joining a team on deathmatch does not crash the server. They run in about a minute, and they are the only reason it is safe to change any of this.

What is not there

HTTP from outside the house (the Cloudflare rule was added on 7 September; the ICE tunnel was already in place). A named admin list — every browser player is an AMX Mod X operator by way of VALVE_ID_LAN. HTTPS on the LAN. Any notion of a map beyond "a .bsp on disk". The three legacy containers, waiting to be retired. And the museum, which is everything from §9 on.

4. Upstream: yohimik, FWGS, and the pieces underneath

This project is a thin layer over other people's work. Knowing who they are, what state each piece is in, and which of them would notice if we asked them something is most of what "maintainable" means here.

The engine lineage

Xash3D is Uncle Mike's 2008–2015 reimplementation of GoldSrc, the Half-Life engine, written from the leaked 2003 source's public description and a great deal of black-box work; the source headers still say "Copyright (C) 2008 Uncle Mike" and GPL v3. Xash3D FWGS is the Flying With Gauss fork (a1batross, mittorn and others) that took it cross-platform from 2015 — Android first, then everything — and is the only living line. It has 2,763 stars, commits the day this was written, and no releases: it ships continuous builds. hlsdk-portable is FWGS's portable Half-Life SDK, under Valve's SDK licence. cs16-client is Velaron's reverse-engineered Counter-Strike 1.6 client for platforms Valve never shipped it on — Android, PS Vita, and, through yohimik, the browser — GPL v2 with the Valve-linking exception, committed to the day before this was written (414 stars).

The web has a longer history than yohimik's. mittorn ported the old Xash3D to Emscripten around 2016–17; it ran Half-Life's Uplink and deathmatch in a tab and was re-uploaded to GitHub by half a dozen people after the original disappeared (btarg, skunksecond, Eman10826; a tutorial video; a page at flash.bannmannutt.com that still serves it). When steren opened issue #1226, "Official WebAssembly / WASM support", in January 2023, a1batross answered within hours:

Working with Emscripten in old engine was fun, and that's it. Some of the code carried over to new engine but it's probably long broken. I don't mind having Emscripten support, but I don't have time to work on it myself. As @mittorn very much absent from engine development (and I understand why), I don't know who else can start working on it.

Five days later, told that play-cs.com had a working client and server, he closed the issue: "Meh, they are probably not going to contribute anything back and they still use old engine version… ports are better be discussed when there is already work done." The thread was reopened in spirit in December 2024 by people wanting a web build ("Annoying as hell someone ported it and didn't give back… Nightmare for preservation and modernization"), Velaron among the repliers; a1batross's position was "work on this yourself, or sponsor it", and, to someone who wanted a personal web client: "can I ask why you so desperate about web port? Why not just play on your machine?" That is the upstream's view, stated plainly and consistently: a web port is welcome as somebody else's work. There is no emscripten branch in FWGS's repository today.

yohimik, July 2025 – August 2026

Seven months after that December thread, yohimik (semyon_f) published webxash3d-fwgs: a monorepo that built FWGS's engine with Emscripten, wrapped it in a TypeScript class, and published four npm packages — xash3d-fwgs (the engine), hlsdk-portable, cs16-client, and later webxash3d-mserver. The first version is dated 13 July 2025; cs16-web's initial commit is 9 August, and its client is byte-for-byte xash3d-fwgs@1.0.1 and cs16-client@0.0.2, extracted from his Docker image on about 11 August.

6. The code, honestly

About three thousand lines across Go, TypeScript, Python and shell in cs16-web, plus fourteen hundred of C# and twenty-five YAML tool specs in darkoak. Small enough that one person can hold it. What follows is what a reviewer with no stake in it would say.

Relay (Go, web-server/go-webrtc-server/)

sound The design is right and the code is now honest about it: a session is one of each thing, packets are copied and never interpreted, the data channels are unordered and unreliable as the game assumes, and the hot path has no allocation per packet beyond the buffer reuse. The tests are worth more than the code — the pion-as-browser round trip means "does the relay still relay" is go test.

to look at server_manager.go is the one 2025 file that survived and reads like it: the three query-packet formats it tries in sequence, the "legacy" parser, the game-mode-from-hostname guess (detectGameMode returns "deathmatch" for any name containing "dm", so a server called "Admin" would be deathmatch). Discovery scans thirty-one ports every three seconds with a goroutine each; harmless at this scale, silly at a hundred servers. The registry keys sessions by a fake four-byte "IP" because the 2025 code did; a session id would do. The directory is still called go-webrtc-server and the module cs16-webrtc-relay; it should be relay/.

missing No authentication on signalling: anyone who can reach port 27100 can open a session to any discovered server (the server's own sv_password is the only gate). No rate limit on sessions. No TLS — the LAN address is plain HTTP, which also means no pointer lock on some browser configurations and no clipboard. All three are fine in a house and none is fine on the internet; the plan puts them where they belong.

Client (TypeScript, web/)

sound Four files, no framework, no dependencies beyond the engine, JSZip and Vite. The transport is upstream's design and can be compared with upstream's code line by line. The join/leave/switch lifecycle with generation counters is careful. The watchdog that infers a refused join from packet counts is honest about being an inference.

to look at Loading is the weak point, and it is upstream's design: the whole zip is fetched, inflated on the main thread with JSZip, and written file by file into MEMFS. 4,126 files, ~464 MB of RAM before the engine allocates anything, every visit. There is no per-map loading, no worker, no IndexedDB cache of the unpacked tree. Elkhan-Isayev's analysis measured the same shape and called the unpack "the #1 perceived fix"; the bar we added makes it visible, not shorter. The picture setting works by overriding devicePixelRatio globally before the engine starts, which is a hack that happens to be the only thing that worked in 2025 and still is. The engine's own console is invisible to the page; that is why __xash is on window and why the tests drive it with Cmd_ExecuteString.

missing Touch controls (upstream had them; not wired). Any in-page settings beyond picture. Any way to see who is on a server before joining. Mobile Safari has not been tried.

Servers (cs-server/)

sound Content mounted, configs mounted, one image, secrets rendered at start and nowhere else. Modes as text. The current.cfg-from-amxx.cfg mechanism is the one non-obvious piece and it is commented at every end.

to look at shared/ is 1.7 GB of files with no manifest and no provenance: 351 maps, of which 74 de_, 46 cs_, 43 fy_, 32 aim_, 20 awp_, 18 gg_; 103 wads in wads/ and the same 103 again at the top level; 24 .res files for 351 maps, so most maps' dependencies are unknown to any tool; the packager found six maps whose wads exist nowhere. The plugin set is 2013's. users.ini grants full admin to VALVE_ID_LAN, which is every browser. shared/addons/amxmodx/plugins/ and every .so are git-ignored, so a fresh clone cannot build a server — the repository does not contain the server.

risk Every player is an operator. With amx_default_access "z" and VALVE_ID_LAN in users.ini with every flag, any browser can amx_map, amx_kick, amx_ban, amx_cvar. The 2025 note said "don't go public with it"; with the tunnel open it is public to anyone who has the password. Reunion can hand out per-address identities instead (cid_RevEmu2013 = 4), but every browser arrives from the relay's address, so that needs the relay to tell the server who is who — which is the same problem as named admins and is one piece of work, not two.

Found and fixed, 7 September 2026: the three-player mixup. Three people joined main from outside on the evening of the 6th with three different names; two ended up with the same name on the server, and one kept being dropped and rejoining, sometimes under someone else's name, until they gave up. The cause is in ReHLDS, sv_main.cpp, SV_ConnectClient under REHLDS_FIXES: a new connection is taken to be an existing player reconnecting when it comes from the same IP address and that player has been silent for ten seconds — and the newcomer is given the absent player's slot, name included. Every browser reached the server from one address, 172.18.0.1, because Docker's port proxy stood between the relay and the container. So whenever one of you stalled for ten seconds, or closed a tab, the next person to connect became you. Reproduced on demand: join as "alpha", close the browser, wait twelve seconds, join as "beta" — the server logs :reconnect, drops alpha, and beta enters the game as alpha. The fix is two small things: the relay now sends each session from its own loopback address (127.0.0.2, .3, …, which Linux allows without configuration), and the main container runs in the host's network so the server sees those addresses rather than the proxy's one. The same reproduction then shows two players, two slots, two names; it is a Playwright test now. Reunion still gives everyone the same identity (VALVE_ID_LAN — every browser presents the same emulated auth key), which is harmless for play and is the "named admins" item in the plan. The same fault had a second home — players arriving through the Steam tunnel all reached the server from the tunnel's one address — and that is closed the same way, by an ingress in the relay that gives each of them an address of its own (§3).

7. Performance: what the numbers say

Two separate problems have both been called "lag" in this project's history: the iMac that stutters (rendering), and the feeling that shots land late (latency). They have nothing to do with each other and the second one is finally measurable.

Latency: it is not the network

measure_lag reads two hops at once. The game ping is what the engine itself reports for a player — a full round trip through relay and server, as the player feels it. The browser-to-relay figure is ICE's own round-trip measurement of the first hop alone. With the browser and the server on the same machine, the network cost is nil, so whatever remains is the pipeline. Three things fall out. The first hop is free: under a millisecond every time, so ICE, DTLS and the data channel are not where the time goes, at least on loopback (on a real network they add whatever the network adds, and no more). Frame rate does not matter: 30, 100 and 200 fps give the same ping, so the engine is not stalling its network on rendering. The server's update rate is the lever: 100 updates per second gives 47 ms, 60 gives 43, and 20 gives 21 — and it is updaterate, not cmdrate, since 100/20 is 43 and 20/100 is 21.

What that most likely means: the game's ping is measured from a server frame's send time to the acknowledgement of it in a client command, and with the server sending a hundred snapshots a second into a path that the browser drains once per event-loop turn, snapshots queue — in the SCTP channel, in the engine's incoming ring buffer, or both — and the acknowledgement of each is late by however deep the queue is. Send fewer, and each is acknowledged sooner. It is a hypothesis; it fits every row.

Whether 20 updates a second feels better is a different question that a headless browser cannot answer: 20 Hz means 50 ms between world snapshots, and the client interpolates across them (ex_interp, default 100 ms), so the picture is smoother but older. CS 1.6 was played at cl_updaterate 20 on dial-up and at 100 in leagues; 30–40 was the common LAN setting. The right experiment is on an iMac with a person holding the mouse: 100, 60, 40, 30, 20, and ask which feels best. The room can set them (set_cvar for the server side; the client reads userconfig.cfg from the zip, so the client side is a packager option or a lobby setting).

Beyond the rates, the levers are, in order of promise: (1) make the engine drain its incoming buffer more than once per frame, if that is where the queue is — a change to the TypeScript Net layer we already own; (2) the server's sys_ticrate (100) and sv_maxupdaterate (101), which bound what the client can ask for; (3) the relay's per-packet path, which is already a straight copy and is unlikely to be measurable. Not on the list: the network, which yohimik's own transport benchmark ranks WebRTC data channels first on round-trip anyway.

Rendering: the iMacs

The 2025 finding stands and the mechanism is understood: a 5K iMac has a device pixel ratio of 2, the engine draws at the canvas's backing-store resolution, and drawing 14.7 million pixels a frame on an Intel iGPU is what "sputters" means. Clamping devicePixelRatio to 1 before the engine starts quarters the work and was the only thing that helped. It is now the lobby's default. The remaining rendering levers are the engine's own cvars in userconfig.cfg — gl_vsync, r_decals, cl_himodels, detail textures — which the 2025 PERFORMANCE-OPTIMIZATION document lists correctly and nobody has measured, because there is no way to measure "sputters" headlessly. The number to collect is the engine's own fps counter (already on screen, cl_showfps 1) on each iMac, before and after each setting.

Loading

Measured by Elkhan-Isayev on the same design and confirmed here: the download is not the wait, the unpack is. 4,126 files inflated by JSZip on the main thread into MEMFS, every visit. The fixes, in order: per-map bundles (§8) so a first visit is the base 100 MB and a map is a few; unzip in a Web Worker so the page stays responsive; cache the unpacked tree in IndexedDB so a second visit is seconds. The last two are upstream-shaped work on the loader, which we own now.

Capacity

One browser is ~half a gigabyte of RAM and a WebGL context on the visitor's machine. The relay is a goroutine pair and a UDP socket per browser. A server is a core for eight players. The house can host a hundred players; the question is only whether a hundred browsers can each hold the game, and that is the per-map loading again.

8. Flexibility: servers on demand

The goal is that dozens of people can each start a server from a map they loved, with a configuration that suits it, and have it go away when they are done. Today there is one server whose personality is a directory. The distance between the two is smaller than it looks, because the 2026 work already moved everything that varies out of images and into text.

What a server is, as a record

server:
  id:        rats-night-2026-09-12          # the container is cs16-<id>
  owner:     shane                          # who may stop it and change it
  mode:      ffa-dm                         # one of modes/*.cfg, or an inline set of cvars
  maps:      [de_rats_1337, de_rats2, cs_rats2_final]
  first:     de_rats_1337
  players:   8
  password:  "…"                            # per server; the lobby carries it
  plugins:   [csdm, csdm-equip]             # what to load, from a known set
  overrides: { sv_gravity: 500 }            # a few cvars on top of the mode
  lifetime:  idle 30m | until 23:00 | pinned
  port:      27032                          # allocated from a pool
  created:   …   by: … (the journal)

Everything in that record already exists somewhere: modes are files, maps are on disk with a manifest saying which the client carries, passwords are rendered by the entrypoint, ports are what discovery scans. What does not exist is the thing that turns the record into a container and back — and that is one Docker API call to create a container from the one image with a generated config directory mounted at /config, plus one to remove it. The room already speaks to Docker's socket for start and stop; create and remove are the same API.

The pieces, in order

1. A config generator.
Given the record, write a directory: server.cfg (hostname, password, maxplayers, the mode's cvars, the overrides), plugins.ini for the chosen plugin set, mapcycle.txt, the mode's addons. Twenty lines of C# or Python; the entrypoint already consumes exactly this shape.
2. A port pool.
27015 stays the family server. Ephemeral servers take 27030–27099. Discovery's scan range widens to match — or better, stops scanning and asks the room, which knows what it created. The relay's RELAY_PRIMARY_PORT becomes "the one the lobby shows by default" and the lobby grows a list again, this time of museum servers with names and descriptions, not ports.
3. Lifecycle.
A job in the room: every minute, any server past its lifetime with nobody on it is stopped and removed, and its record kept. The sampler already reads player counts every minute; this is one more branch.
4. Tools.
create_server(mode, maps, password?, lifetime?), destroy_server(id), get_servers (the records, live state beside them). The existing per-server tools take the id. All journalled, as everything is.
5. The client's zip.
This is the real constraint. A browser must have the map before it can join, and today "having" means "in the 274 MB zip it unpacked". Three options, in increasing effort: (a) one zip with the union of every server's maps — grows without bound, and the RAM cost grows with it; (b) a base zip without maps plus per-map bundles the page fetches on demand and writes into MEMFS before connecting — the engine loads the map when the server tells it to, and by then the file is there; (c) lazy loading inside the engine, which upstream's README lists as a TODO requiring EAGAIN support and nobody has done. (b) is the right one and it is not hard: the packager already computes each map's dependencies, and the lobby knows which server it is about to join. It also makes the first visit 100 MB instead of 274.

Resource envelope

One idle ReHLDS container is ~60 MB RSS and no CPU; with eight players it is one core's worth of a 100 Hz loop at most. The relay is one goroutine pair per browser. mainbrain has 12 cores and 94 GB; a dozen servers with a few players each is nothing, and a hundred would be a scheduling question, not a hardware one. The browser is the expensive end: half a gigabyte of RAM per tab and a WebGL context, which is why the client zip and the per-map loading matter more than anything on the server.

What flexibility should not mean

Not arbitrary uploads of configs or plugins by visitors — a plugin is code that runs as the server. Not arbitrary cvars — set_cvar already refuses the ones that are the room's own door. The record's plugins field chooses from a curated set; overrides is a short allow-list of gameplay cvars. The person creating a server picks from a menu that you wrote.

A record is a row in a database and a directory of files. The database is the room's — cs16.db already holds samples, events and the journal, and a catalogue table beside them costs nothing and is immediately queryable through query_cs16_sql. The files stay in cs-server/shared/, which is where the servers already look, with the manifest the packager writes becoming the catalogue's view of what the client carries.

Provenance: where the history comes from

Most of what a museum says about a map is on its 17buddies or GameBanana page: author, upload date, description, screenshots, comments, download count. Both are alive; 17buddies claims 59,209 HL1 maps. A map's own .txt often has the author's name and email from the year it was made. The .bsp itself carries a little — the worldspawn entity has message (the title shown on load) and sometimes a mapversion; the wad list names the mapper's tools. An import step that reads the readme, hashes the files, looks the name up on both sites and records the URLs and what they say is most of the provenance you will ever have, and it is a script.

Previews in the browser, without the engine

Two things exist and are maintained: web-hlmv (MDL models, textures, animations, WebGL, updated August 2026) and several BSP renderers, of which bspview is the most-starred and urgorri/goldsrc-bsp-viewer the most recent (three.js, September 2026); lewa-j/hlbsp-converter turns a BSP into glTF, after which any viewer works. A preview page for a map is a canvas with one of those, the overview image, and the record. It does not need the engine, valve.zip, a server, or WebRTC, so it is cheap to open and works on a phone. That is the page most visitors will spend most of their time on.

Access

Invite-only by construction, not by policy: the site behind a password (the same mechanism as the admin key today, or a per-person link), each server behind its own sv_password which the lobby carries, and the relay refusing signalling without a token the site issued. That is three checks and none of them is exotic. "Not-quite-public" then means: the page is reachable, and nobody gets past the first screen without a word from you.

10. The cheats, as research

You are curious how they worked, and you want them only on your own servers, with your own client. Both of those are easier here than they ever were on Windows in 2003, and the reason is instructive: the client is ours. Every classic CS 1.6 cheat was a way of getting at the client's memory or its rendering from outside the process. In this project the client runs inside a page we serve, its memory is a JavaScript-visible ArrayBuffer, its renderer is a WebGL context we hand it, and its console is a function call. Most of what took a DLL injector in 2003 is a few lines of TypeScript here — which is the whole research point, and also exactly why it can never be allowed near a server that other people play on.

What they were

Wallhack (XQZ, "Asus walls", 2001–03)
The first ones were not even cheats in the client: an ASUS graphics-driver feature let you make walls translucent in any OpenGL game, and people noticed. XQZ (2002) did the same by hooking opengl32.dll — a "wrapper" that sat between the game and the driver and drew world polygons with depth testing off or with transparency, so players showed through walls. It worked on any game that used OpenGL that way, which is why it spread so far.
ESP
Boxes, names and health drawn over players through walls. The client already knows where every player is (the server sends entity positions, subject to PVS), so an ESP is: read the client's entity table, project through the view matrix, draw. Same hook as the wallhack, different output.
Aimbot (OGC, 2001–06)
OGC was the one everyone had. Read the entity list, pick a target by angle or distance, set the view angles (or nudge them — "smooth" aimbots, to look human), optionally fire. Later ones read player bones for headshots. "Nospread" and "norecoil" were the same idea applied to the weapon cone. It hooked the client DLL rather than OpenGL.
Speedhack
Lie to the engine about how much time has passed, so more movement commands are sent per real second. Trivially detectable once servers checked for it.
The other side: Cheating-Death (2002–06), HLGuard, VAC (2002, permanent bans from 2005)
Cheating-Death (UnitedAdmins) ran on the client and the server and refused clients that did not pass its checks — the first "kernel-ish" anticheat many people ran. HLGuard was server-side, and its most interesting feature is the one that matters to a museum: anti-wallhack by not sending what you cannot see — the server stops transmitting entities behind walls, so no client-side trick can draw them. That idea, PVS-tight visibility on the server, is the only kind of anticheat that works against a client you cannot trust, which is every browser.

Containment, which is not optional

A cheat page is a different build of the client served at a different path (/lab), loaded only with a key, that will only sign on to a server whose record has lab: true. Phase 1 (the room) and the first half of phase 2 (modes, outside play) are done. What follows is the rest of phase 2 and phase 3 as one sequence, ordered so that each step is useful on its own and the museum grows out of the game rather than beside it. Days are working days for one person with the tools of September 2026; each step ends with tests green and the servers up.

Phase 2b — foundations the museum needs (≈ 6 days)

14. Running the server from inside the game

You do not have to leave the game to change it. Everything below was run against cs16-main from the browser client on 7 September 2026 and does what it says.

The console

Press ~ in the game. The engine's console drops down over the top of the screen with a ] prompt; type there and press Enter, ~ again to close it. It is the same console the desktop game has, and it works in the browser tab — that is where the AMX Mod X replies appear ([AMXX] Cvar "sv_gravity" changed to "400"), alongside the server's own chat line telling everyone what you did.

Two menus save a lot of typing, both driven by the number keys:

  • amxmodmenu — the main menu: CSDM Menu, Kick Player, Ban Player, Slap/Slay, Team Player, Changelevel, Vote for maps, and more on page 2.
  • amx_mapmenu — straight to the map list. Note that this list comes from addons/amxmodx/configs/maps.ini (de_dust2, de_dust, de_aztec, …), which is not the mode's rotation in modes/<mode>.maps. Either list is fine to pick from; the menu simply knows a different one.

What sticks and what does not

This is the part worth remembering. A cvar you set in the game lasts until the map changes — because amxx.cfg re-runs modes/current.cfg on every map load, and every mode file sets the whole list: gravity, air acceleration, max speed, bunny hopping, round time, freeze time, start money, buy time, free-for-all, CSDM and GunGame. A cvar that no mode file mentions (mp_friendlyfire in most modes, say) survives map changes and dies at the next server restart.

To make a change permanent, put it in the mode: cs-server/main/modes/<mode>.cfg, one cvar value per line. That file is the mode's definition and the only thing that survives everything.

And the mode itself cannot be changed from inside the game — a mode is a set of files plus the line in current.cfg. That is set_mode in the room, which also picks the first map. From the room: set_mode, change_map, set_cvar, get_cvars, say_to_server, kick_player, get_players, run_rcon_command for anything not covered.

Two things to know before you type

Everyone is an admin. The image's users.ini gives the identity VALVE_ID_LAN every flag there is, and every browser player is VALVE_ID_LAN (§6). So anyone who has the server password can run every command on this page. Inside the family that is merely untidy; it is the reason "named admins" is early in the plan.

Avoid rcon from the game console. It works — rcon_password … then rcon sv_gravity 400 — but the password is then in the client's config and in the server's log in plain text. The amx_ commands need no password because you are already recognised, and the room needs none because it holds its own.

15. Could the relay point at somebody else's server?

An idea worth writing down rather than building: you host the relay, and it bridges browsers to a Counter-Strike server that is not yours — a public one, somewhere on the internet. Mechanically it is almost free. The relay interprets nothing; it copies datagrams between a data channel and a UDP socket, and the socket's destination is a host and a port in a config value. Point it at 203.0.113.7:27015 instead of 127.0.0.1:27015 and the browser cannot tell. Discovery already speaks the game's own query protocol, which is exactly how every server browser in the world lists remote servers, so listing them is free too. Others have already gone this way: bordeux's Rust proxy is written to sit in front of any server, and webXash simply asks you to type an address.

So the interesting question is not whether it runs. It is what happens when it does.

Four things that break, in order of how quickly you would meet them

  1. Content. The browser plays out of valve.zip — a fixed set of maps, models and sounds baked at packaging time. A stranger's server runs de_dust2_2x2_final3 and a custom knife model, and your client has neither. A desktop client would download them from the server or from its sv_downloadurl; in a tab the first is slow and usually disabled, and the second is an HTTP fetch from a host that would have to send CORS headers it has never heard of. In practice you could join servers that run stock maps and nothing else, which in 2026 is a small and shrinking set.
  2. They will not let you in. Public servers that survive run Reunion or similar, and the common setting for a non-Steam client is cid_RevEmu = 5, which means "rejected". Ours is exactly that kind of client. The servers that would accept it are the no-Steam ecosystem, which is large in some regions and mostly not the servers anyone is nostalgic for.
  3. Everybody is one player. This is the sharpest one, and today's bug taught it. To a remote server, every browser you relay arrives from your house's one IP address. We fixed that here by giving each session its own loopback address and putting the server on the host network — neither of which you can do to a machine you do not own. So on a stranger's server your players would take each other's slots and names exactly as they did on the 6th, and worse: one of them gets banned and all of them are banned, because a ban is an address. From the far end you look like a proxy with a dozen people behind it, which is indistinguishable from the thing their admins ban on sight.
  4. The room goes blind. Modes, map changes, cvars, kicks, the log tail, player history — all of it is rcon and log files on a server you control. Against someone else's server the relay is a dumb pipe and darkoak has nothing to say about it.

The latency, which is arithmetic

Relaying adds a leg. A player who could reach the server in 40 ms now goes player → your house → server: their distance to you, plus your distance to the server, plus the pipeline cost measured in §7. If you, the players and the server are all in one country it is a modest tax. If the server is in Frankfurt and the players are in California and the relay is in Ohio, you have built a trombone and everyone pays for it twice. The only arrangement that is honestly better than a direct connection is one where the relay is near the server and the browser's path to the relay is the good part.

The home ISP, which is also arithmetic

Measured here on 7 September, one player standing in a live game, read from /api/sessions over twenty seconds:

DirectionRatePackets
server → browser15.7 kB/s ≈ 126 kbit/s28/s
browser → server1.3 kB/s ≈ 10 kbit/s42/s

A relayed player costs the relay that much twice over — once receiving it, once sending it on — so roughly 0.14 Mbit/s in each direction per player, and about seventy packets a second each way. Ten players is 1.4 Mbit/s up; thirty-two is 4.4; a hundred is 14. A cable upload of twenty or thirty megabits is not the constraint, and neither is the CPU: a Go loop copying 14,000 small packets a second is nothing. Three other things are the constraint. Packet rate through the house's router, where consumer NAT tables and cheap hardware are much less happy about 14,000 pps than about the same bytes in fewer packets. Bufferbloat: the moment somebody upstairs uploads a video, every relayed player feels it, because they are all sharing one upstream queue — the game is small but it is exquisitely sensitive to jitter, and a home connection has no queue discipline worth the name. And playit, which currently carries the outside traffic and would carry all of this too, out to their edge and back, doubling the WAN cost and adding their own hop and their own limits.

What is actually worth doing instead

  • Relay next to the server. If the goal is "let browsers play on server X", the right place for the relay is X's datacentre, not your study — a few dollars a month, one hop, no trombone. This is what play-cs.com and CSJS do; it is why they are fast.
  • Give the relay away. The thing a server owner wants is a browser front door for their server, which they would run themselves. Ours is 1,300 lines of Go with tests and could be a container someone else runs — the shape yohimik's cs-web-server image had, and the reason so many of the projects in §5 are that image with compose files around it.
  • Point at servers you rent, not servers you find. The same code, with rcon and logs and identity intact, is how a museum with more than a house's worth of visitors would run: the room creates a server on a rented box for an event, the relay bridges to it, everything else works as it does now.

Verdict. Two hours of work to make it possible; one evening to discover that content mismatches and rejected authentication mean you can join almost nothing, and that the servers you can join will ban you for looking like exactly what you are. Worth keeping in the back pocket for a server whose owner says yes — and in that case, ask them to run the relay.
